# ns-ticket-intel (Cluster B)

Bulk diagnose-once over the cluster-B ticket working set, then project P6 / P11 / P12 / deploy-gate off that one in-context cache. Night-shift process **Cluster B** (P4B + P6 + P11 + P12); also runnable on demand.

This skill loads the **Atlassian MCP** (Jira) and the **deploy-verify engine** at run time via `ToolSearch` / Bash — `allowed-tools` deliberately omits `Skill`: the working set is diagnosed in ONE shallow×many pass IN-CONTEXT (citing `03 Resources/reference/diagnosis-procedure.md`). Do NOT invoke a per-ticket diagnosis sub-skill — that would defeat diagnose-once and regress the consolidation.

## Invocation
Invoked by the `night-shift-fanout` workflow as `/ns-ticket-intel for LOCAL=<date>`, with `schema: CACHE_SCHEMA` on the `agent()` call. Runnable solo: `/ns-ticket-intel` (defaults `LOCAL` to today; solo = the on-demand behavior in "Solo run" below).

**Cache return (critical).** When invoked by the workflow, this skill ALSO returns the diagnosis cache as a structured value — the workflow's `agent()` call carries a `CACHE_SCHEMA`, and the captured return is shaped `{ cache: [...rows], p6, p11, p12, needsKyle }`. The workflow passes that `cache` array straight in-prompt to the **P5** (ASD triage) and **Cluster C** (theses + patterns) agents — no report round-trip. So the cache is produced in BOTH forms, both required: the structured RETURN VALUE (consumed in-workflow) AND the `## Diagnosis cache` Markdown table in the artifact (for the human reader). See the P4B brief's "PRODUCE the diagnosis cache in TWO forms" instruction below — that is the source of truth for the dual form.

## Artifact contract (PRIMARY OUTPUT)
Resolve `LOCAL` (from the invocation, else `TZ=America/Denver date +%Y-%m-%d`). Write `00 Inbox/<LOCAL>-ns/clusterB.md` with frontmatter `process: clusterB`, `status: complete|failed`, an optional `needs_kyle:` list, and a body = the **P6** section + the **P11** section + the **P12** section + the **`## ASD reopened overnight`** callout (when non-empty) + the `## Diagnosis cache` table text (the table sourced from the P4B coordinator step). This artifact is the source of truth FINALIZE splices into the consolidated report (and appends the `## Diagnosis cache` table at the report bottom, for the human reader). Do NOT commit/push; honor Confidential/ strict mode. Do NOT rewrite the shared consolidated report file.

Also capture `dow` = `TZ=America/Denver date +%u` if any day-gating is relevant; Cluster B itself runs nightly (no day gate).

## Procedure

The four briefs below are lifted verbatim from the night-shift orchestrator. `<LOCAL>` and `<P>` are resolved at run time per the Artifact contract above (not at author time). P4B is the shared-read coordinator that produces the cache + table; P6/P11/P12 are the report sections projected off that in-context cache.

PROCESS 4B — CLUSTER B PRE-FETCH + DIAGNOSIS CACHE (shared read for P5/P6/P11 + the P12 QE-severity projection; consolidation Phase 2, 2026-06-13). This is a SHARED-READ COORDINATOR, not a monolith: it pulls + diagnoses ONCE, then the projections each read the cache and are independently failure-wrapped. If THIS step errors, log it and let each projection FALL BACK to diagnosing its own scope (degrade, never abort the shift).
- ONE Jira pull of the cluster-B working set (cloudId `porchsoftware.atlassian.net`; load the Atlassian MCP via ToolSearch), deduped into a single unique-ticket list with EJA↔ASD mirror pairs keyed together. Constituent queries: ASD open set (for P5) · EJA created/reopened ≤24h (for P6) · ALL open EJA+ASD Blocker+High (for P11) · **ASD reopened ≤12h** (the overnight callout below).
- **ASD reopened ≤12h — the overnight callout.** EDJ's QE team works from India (IST = MT + 12½h), so they test through Kyle's night; the shift fires ~12:17 AM MT and the 12h window covers their working day. **This is NOT the P6 query** — P6's `status changed to ("Reopened","Open") after -1d` is scoped to **EJA**; this one is ASD and nothing else covers it. Use **both halves** (`project = ASD AND status = "Reopened"`, and `project = ASD AND status CHANGED TO "Reopened" AFTER -12h`) — status-only misses every ticket that was reopened and has since moved on, which is most of them. The reopen reason is in the **comments**, not `customfield_10078` (which does not exist on ASD): the comment lands within seconds of the transition, and it is quoted **verbatim with sender and timestamp**. `tl-wave-sweep` §5d is the single home for this rule — the field ids, the changelog gotcha, the three disagreeing priority fields and the wave scoping all live there; read it rather than re-deriving. Surface the findings as their own **"## ASD reopened overnight"** section in the `clusterB.md` artifact, and it is **Needs-Kyle-eligible** — a `Blocker` or a `Ph1-TL-W1` reopen is decision-grade by definition, so it goes in the artifact's `needs_kyle:` list. Standard Cluster B discipline: **report only** — no promotions, no transitions, no comments, no Jira writes of any kind.
- **PAGINATE TO COMPLETENESS (2026-07-08 — run 39 truncation fix).** The Blocker/High query exceeds `maxResults=50` — run 39 returned exactly 50 with `isLast:false`, silently truncating the **High tail** (all 4 EJA Blockers were safe by priority-DESC ordering, but the diagnosed-High set was incomplete and the cache had to flag it). For EACH constituent query, **loop until `isLast:true`** (advance the pagination token, or `startAt += maxResults`), keeping the **field set identical across pages** (pagination tokens are field-bound and expire — if one expires mid-loop, restart that query from page 1 with the same fields — **cap at 2 restarts**, then record what was captured and note the residual as a bounded partial rather than looping forever), then UNION the pages before the dedup. Record the page count + final total in the artifact so completeness is auditable; only note a truncation if pagination genuinely can't complete (e.g. token keeps expiring), never as the steady state.
- DIAGNOSE each UNIQUE ticket/mirror-pair ONCE via the shared diagnosis procedure (`03 Resources/reference/diagnosis-procedure.md`) at **`shallow×many` depth**, field-rubric per project (EJA→strict-EJA, ASD→opportunistic-ASD). Record its emitted root cause + `file:line` + root-cause confidence (1-5) + repro status + any Kusto K-code into the cache row. (Diagnose the EJA-≤24h set in full; then Blocker+High up to the ~15-20 cap.)
- Also record the **mirror's assignee + status** for each pair (from the `issuelinks`+`assignee`+`status` already pulled) — the ownership-gate input per `03 Resources/reference/diagnosis-procedure.md` → *Mirror-ownership gate*. No extra fetch; it's in the data you already have.
- Also record each pair's **deploy verdict** — whether the fix actually reached UAT — via the `deploy-verify` engine (`.claude/skills/deploy-verify/deploy_tracker_web.py`; the `deploy-verify` skill is the spec). ONCE for the run: `python3 .claude/skills/deploy-verify/deploy_tracker_web.py crawl` (cached; tracker is internal HTTP, no creds). Then per pair, build candidates = the mirror EJA(s) + any **by-proxy carrier named in their closure comments** (e.g. EJA-1869→EJA-1870 — fetch `comment` if you didn't already) + each candidate's `resolutiondate`, and pipe to `... verdict --candidates -`. Record the headline (✅ in UAT / 🟡 promoted-not-UAT / ⚠️ gap / ◻️ pre-window / 🆕 too-new) + carrying key. **Scope: the cluster-B working set only** — NOT the full open-ASD mirror-closeout (that stays the on-demand `/deploy-verify --uat-mirror-scan`). If the tracker is unreachable, record "—" and note it; never abort the shift.
- PRODUCE the diagnosis cache in TWO forms, both required: (1) the structured RETURN VALUE matching `CACHE_SCHEMA` — `cache` is an array of rows, each with `tickets`, `priority`, `rootCause`, `fileLine`, `rcConf` (1-5), `repro`, `kusto`, `mirror` (owner/status), `deployVerdict`; the workflow passes this `cache` array straight to the P5 + Cluster C agents in-prompt. (2) the same data as a clearly-delimited Markdown table in your `-ns/clusterB.md` artifact body — columns `Ticket(s) | Priority | Root-cause hypothesis | file:line | RC-conf (1-5) | Repro status | Kusto | Mirror owner/status | Deploy verdict` (RC-conf = the procedure's root-cause confidence, `/rca` seeds from it; Mirror owner/status = the gate input, e.g. "Ron / Tech Refinement" or "—"; Deploy verdict = the deploy-verify headline + carrying key, or "—") — one row per unique ticket/mirror-pair (mirror pairs on ONE row, e.g. `EJA-3149 ↔ ASD-751`). FINALIZE appends this table at the BOTTOM of the night-shift report (from the artifact) so it never competes with the "Needs Kyle" headline. The P6/P11/P12 projections inside this same agent have the cache in-context; the downstream P5/Cluster C agents receive it in-prompt — none of them re-diagnose what's already cached.

PROCESS 6 — EJA new-ticket view (Cluster B PROJECTION off the P4B cache; REPORT ONLY — no promotions). Distinct from ASD: internal Annuities sprint-bug queue, internal-EJA (QE) lens, NOT the ASD external-tester rubric.
- The EJA created/reopened ≤24h set was pulled + diagnosed by P4B (JQL it used: `project = EJA AND statusCategory != Done AND (created >= -1d OR status changed to ("Reopened","Open") after -1d) ORDER BY created DESC`). READ those findings from the in-context P4B cache (this projection runs inside the same Cluster B agent). For any ≤24h EJA ticket NOT in the cache (e.g. below P4B's cap, or if P4B errored), do a light diagnosis here (read ticket + prior context, grep `~/code/worktrees/main`, trace the data path; Kusto only if a K-code is present).
- Format the "EJA — new since yesterday" section: per ticket, the cached root-cause hypothesis + `file:line`, repro status, and a recommended `/triage` category (needs-triage / needs-info / ready-for-remote / ready-for-kyle / wontfix).
- DO NOT promote to vault dev items, transition tickets, or post Jira comments. Kyle promotes in the morning.

PROCESS 11 — Blocker/High autonomous-fix confidence (Cluster B PROJECTION off the P4B cache; SCORE + REPORT ONLY — no promotions, spawns, or Jira writes).
- The open EJA+ASD Blocker+High set was pulled + diagnosed by P4B (JQL it used: `project = EJA AND statusCategory != Done AND priority in (Blocker, High) ORDER BY priority DESC, updated DESC`, and the same for `project = ASD`; cap ~15-20, Blockers first). READ those root-cause / `file:line` / repro / Kusto findings from the in-context P4B cache (this projection runs inside the same Cluster B agent) — do NOT re-diagnose what's cached. For any Blocker/High not in the cache (below cap, or if P4B errored), diagnose here using the same method (QE repro + fields, Kusto if a K-code, trace `~/code/worktrees/main`).
- Assign **autonomous-fix confidence (1-5)** per the DERIVED rubric in `03 Resources/reference/diagnosis-procedure.md` (root-cause confidence + fix scope + blast radius). Read the cached root cause / `file:line` / repro; do not re-diagnose.
- Report a consolidated **"## Blocker/High — autonomous-fix confidence"** section, **sorted by priority DESC then confidence DESC** (priority leads; confidence is a within-tier tiebreaker, NEVER the primary sort — fix-confidence measures *fixability*, not importance, and confidence-first ordering wrongly floats clean low-severity bugs above scoped Blocker/High work). Present **priority and confidence as two distinct columns**, not one fused ranking. Per item: **ticket linked** (`https://porchsoftware.atlassian.net/browse/<KEY>`) + priority, root-cause hypothesis with `file:line`, repro status (from QE info), diagnostics run (Kusto K-code if any), **confidence N/5 + one-line rationale**, recommended next action.
- **Gate tag, not severity invention:** P11 only reports tickets already at Blocker/High priority, so do NOT relabel a Medium as above-gate. Instead, the "spawn-ready residue" callout (the items pitched as actionable next actions) is the subset that is BOTH genuinely fix-needed (not in-flight) AND ≥ the autonomy-confidence floor — keep that callout ordered by priority, and explicitly exclude in-flight / needs-Kusto / human-decision items from it so the headline can't read as "do this Medium first." (Severity *re-rating* of mis-filed Mediums is P12's job, not P11's.)
- **Apply the mirror-ownership gate to the spawn-ready residue** (per the diagnosis procedure): exclude any ticket whose **Mirror owner/status** cache column shows an assigned mirror in active sprint flow (Tech Refinement / Work Is Scheduled / In Progress under an owner) — it's **owned elsewhere**, not spawn-ready, no matter how high its fix-confidence. Keep its score in the table (mark "owned: `<owner>`/`<status>`"); just keep it out of the actionable callout. This is the guardrail against re-flagging owned work (added 2026-06-22 — the ASD-971/974 → EJA-3252/Ron case).
- **Apply the deploy gate to the spawn-ready residue too** (the **Deploy verdict** cache column; added 2026-06-22 off the `/deploy-verify` build — closes the "Done ≠ deployed" blind spot): if the mirror is **✅ in UAT**, the fix already shipped → exclude from spawn-ready (mark "deployed: in UAT"). If it's a **⚠️ genuine gap** (Done in-window but in no env), it's a **deploy problem, not a code problem** → route it to a separate **"## Deploy gaps (deploy-it, don't re-fix)"** Needs-Kyle callout, NOT the fix-spawn callout. Only ◻️ pre-window / 🆕 too-new / "—" (no verdict) items fall through to normal fix-spawn evaluation. Remember the verdict is commit-key-attributed (a ⚠️ is "verify," not proof) — surface, don't auto-act.
- SCORE + REPORT ONLY: do NOT promote to dev items, add to the queue, spawn worktrees, transition tickets, or post comments. Kyle decides what to spawn from the scores in the morning.

PROCESS 12 — QE-severity calibration (Cluster B PROJECTION off the P4B cache; RECOMMEND + REPORT ONLY — no Jira writes). Idea: `00 Inbox/2026-06-12-qe-severity-validation-idea.md`.
- Scope: newly-QE-filed bugs awaiting PO severity-validation — especially the EJA *Bugs To Triage* board (the EJA-3174 intake lane). Pull this board's open set (Atlassian MCP). NOTE: this board is NOT one of P4B's constituent queries, so most of these will NOT be cached — P12 must cover them itself.
- For each in-scope ticket: if it IS in the in-context P4B cache, reuse that root-cause / repro; otherwise do a light self-diagnosis here (read the ticket + repro, quick `~/code/worktrees/main` trace) — same fallback discipline as P6/P11. Assess blast-radius from the affected `file:line` / component.
- Recommend a right-sized severity (Blocker / High / Medium / Low) per item with a one-line rationale. Flag clear mismatches (a cosmetic bug filed Blocker; a data-corruption or workflow-blocking bug filed Low).
- REPORT ONLY under a "## QE-severity calibration" section. Do NOT edit ticket severity or post comments — Kyle / the PO decide. If the board is empty/unreachable, note "skipped — no tickets to calibrate" and move on.
